# Этап 5 — внедрение и поддержка информационной системы ГОЧС

## 1. Назначение

Документ описывает выполнение этапа 5: подготовку системы к внедрению, развёртывание, обучение пользователей и сопровождение после запуска.

Система представляет собой единое web-приложение для учёта и планирования мероприятий ГО и ЧС. Она объединяет общий кадровый справочник, СИЗ, НФГО, защитные сооружения, эвакуацию, обучение, приказы, отчётность, пятилетнее планирование закупок и специальный режим.

## 3. Что внедряется

```text
Браузер
  ↓
ASP.NET Core 8
  ↓
модули бизнес-логики
```

Функциональные области:

4. списание и утилизация;

13. внутренние уведомления;
14. вложения;
15. аудит;
16. экспорт документов.

## 4. Что не следует заявлять без отдельной доработки

- AD/LDAP/OIDC;
- ролевую модель пользователей;
- юридически значимую электронную подпись;
- обмен с государственными ИС;
- внешнюю SMS/e-mail рассылку;
- кластеризацию и high availability;
- несколько экземпляров приложения на одной SQLite;
- антивирусную проверку вложений;
- автоматическое соответствие конкретным нормативным формам МЧС без предметной сверки.

## 5. Ответственность

Названия ниже — организационные зоны ответственности, а не реализованные роли доступа.

| Участник | Ответственность |
|---|---|
| Владелец системы | решение о вводе и утверждение процессов |
| Специалист ГО и ЧС | проверка предметных данных и сценариев |
| Администратор | развёртывание, backup, обновления, доступность |
| Оператор | повседневная работа |
| Тренер | обучение пользователей |
| Поддержка | регистрация и обработка обращений |
| Разработка | исправления и развитие |

ФИО и контакты ответственных утверждаются организацией отдельно.

## 6. Среды

### Разработка

Допускаются seed-данные, Swagger и частые изменения.

### Приёмочный стенд

Используется для пользовательской приёмки, обучения, проверки миграций, backup/restore и релизного кандидата.

### Рабочая среда

Для server mode проект предусматривает Docker Compose, Caddy, HTTPS, закрытую Docker-сеть, Secure/HttpOnly/SameSite cookie, явный `AllowedHosts`, trusted proxy, внешний secret и отключённый Swagger.

Подробности: [DEPLOY.md](DEPLOY.md).

## 7. Пошаговое внедрение

### Этап 0. Организация

До установки назначить владельца, администратора, основного и резервного оператора, канал поддержки, место backup и порядок согласования изменений.

### Этап 1. Инфраструктура

Проверить:

- сервер;
- Docker/Compose либо .NET 8 SDK;
- DNS;
- HTTPS;
- дисковое пространство;
- место внешних backup;
- права secret file;
- сетевые ограничения;
- время сервера.

### Этап 2. Приёмочный стенд

1. Получить проверенную версию.
2. Настроить `.env`.
3. Создать случайный пароль не короче 16 символов.
4. Проверить Compose-конфигурацию.
5. Запустить.
6. Проверить `/api/health`.
7. Выполнить вход.
8. Открыть все основные разделы.
9. Создать backup.
10. Выполнить тестовое восстановление в отдельной среде.

### Этап 3. Исходные данные

Согласовать:

- организацию и категорию ГО;
- руководителя;
- сотрудников и табельные номера;
- подразделения;
- размеры СИЗ;
- смены;
- кадровые статусы;
- состав НФГО;
- укрытия;
- транспорт и пункты приёма;
- склады;
- типы СИЗ;
- цены и сроки поставки;
- контрагентов.

Для импорта сотрудников использовать устойчивый внешний ID (`Source + SourceId`). ФИО не использовать как ключ автоматического объединения.

### Этап 4. Сквозные проверки

#### СИЗ

#### Укрытия

### Этап 5. Приёмка

Использовать материалы `docs/testing`.

Важно: наличие тестового скрипта не равно успешному тестированию. Результат должен быть записан в `TEST_REPORT.md` с датой, commit и окружением.

### Этап 6. Обучение

Оператор должен уметь:

- войти;
- работать со справочником сотрудников;
- выполнить приход и выдачу;
- понимать Draft/Confirmed/Signed/Activated;
- работать с НФГО и укрытиями;
- получать документы;
- понимать ограничения текущей подписи;
- обращаться в поддержку.

### Этап 7. Go-live

Использовать [GO_LIVE_CHECKLIST.md](GO_LIVE_CHECKLIST.md).

Рекомендуемый порядок:

1. заморозить необязательные изменения;
2. сохранить backup;
3. развернуть утверждённую версию;
4. проверить health;
5. выполнить вход;
6. выполнить smoke-test;
7. проверить сохранение данных после restart;
8. создать первый production backup;
9. зафиксировать дату и версию.

## 8. Откат

Нельзя запускать старый бинарник поверх неизвестной новой схемы.

Правильная схема:

```text
backup
→ update
→ migrations
→ smoke-test
```

При неуспехе:

```text
stop
→ restore совместимого backup
→ предыдущая версия
→ smoke-test
```

Проект создаёт backup перед изменением известной старой схемы и останавливается при неизвестной схеме.

## 9. Hypercare

Для первого запуска рекомендуется не менее пяти рабочих дней усиленной поддержки.

В этот период:

- ежедневно проверять health;
- контролировать disk space;
- контролировать backup;
- быстро фиксировать ошибки;
- не выпускать необязательные изменения;
- ежедневно разбирать P1/P2;
- уточнять документацию по реальным вопросам пользователей.

Срок является рекомендацией процесса и может быть изменён организацией.

## 10. Эксплуатационные показатели

Минимум:

- доступность;
- перезапуски;
- свободное место;
- размер БД;
- возраст backup;
- результат restore drill;
- P1/P2;
- открытые дефекты;
- время реакции поддержки;
- результат последнего integration/UI прогона.

Встроенной полноценной системы метрик в приложении нет — контроль организуется внешними средствами или регламентом.

## 11. Критерии завершения этапа 5

- документация передана;
- стенд/сервер развёрнут;
- конфигурация зафиксирована;
- backup и restore проверены;
- тестирование проведено и записано;
- оператор обучен;
- go-live checklist выполнен;
- поддержка назначена;
- ограничения согласованы;
- порядок релизов определён.

## 12. Основные риски

| Риск | Состояние | Действие |
|---|---|---|
| Одна операторская учётная запись | текущая архитектура | для многопользовательского режима внедрить identity + RBAC |
| Нет УКЭП | текущее ограничение | интегрировать ЭП отдельно |
| SQLite / один процесс | текущая архитектура | допустимо для небольшой установки; при росте рассмотреть PostgreSQL |
| Нет malware scanning | текущее ограничение | добавить до внешнего файлового обмена |
| Нет HA | текущее ограничение | определить RTO/RPO и схему восстановления |
| Production deployment не подтверждён | указано в проекте | провести пилот на реальной инфраструктуре |
| Тесты могут быть NOT RUN | текущая документация | выполнить и зафиксировать фактический прогон |
| Формы учебные | текущая документация | предметная/юридическая сверка |
