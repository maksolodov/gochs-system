# Регламент сопровождения и поддержки системы ГОЧС

## 1. Цель

Регламент определяет порядок обработки обращений после запуска: от пользовательского вопроса до восстановления после серьёзного сбоя.

Точные контакты, график дежурств и SLA утверждаются организацией отдельно. В документе приведена рекомендуемая модель поддержки.

## 2. Единый канал обращений

Каждое обращение должно регистрироваться в одном месте:

- корпоративный Service Desk;
- внутренний трекер;
- либо согласованный issue tracker.

Личное сообщение разработчику не должно быть единственным следом инцидента.

## 3. Что указывать в обращении

Минимально:

- дата и время;
- пользователь;
- раздел;
- действие;
- ожидаемый результат;
- фактический результат;
- текст ошибки;
- ID записи/документа;
- скриншот;
- браузер;
- версия/commit;
- повторяемость;
- затронуты ли данные.

Пароль к обращению не прикладывается.

Шаблон дефекта уже есть в [testing/BUG_REPORT.md](testing/BUG_REPORT.md).

## 4. Типы обращений

### Консультация

Пользователь не знает, как выполнить допустимую операцию.

### Инцидент

Ранее работавшая функция недоступна или работает неправильно.

### Дефект данных

Состояние данных не соответствует ожидаемому.

### Запрос изменения

Необходима новая функция или изменение правил.

### Инцидент безопасности

Подозрение на компрометацию секрета, несанкционированный доступ, подозрительный файл или утечку.

## 5. Приоритет

| Приоритет | Пример |
|---|---|
| P1 Критический | система полностью недоступна; БД не открывается; риск потери/компрометации |
| P2 Высокий | ключевой процесс невозможен: вход, выдача, отчёт, restore |
| P3 Средний | дефект отдельной функции с обходным путём |
| P4 Низкий | косметика, консультация, улучшение |

## 6. Рекомендуемые цели реакции

Значения ниже являются предложением для пилотного сопровождения и должны быть утверждены заказчиком.

| Приоритет | Подтверждение | Первый workaround |
|---|---:|---:|
| P1 | 15 минут в рабочее время | до 2 часов |
| P2 | 1 час | тот же рабочий день |
| P3 | 4 рабочих часа | до 3 рабочих дней |
| P4 | 1 рабочий день | плановый релиз |

## 7. Линии поддержки

### L1 — пользовательская

Решает:

- вход;
- навигацию;
- типовые ошибки заполнения;
- поиск нужной функции;
- стандартные сценарии.

Использует [USER_GUIDE.md](USER_GUIDE.md).

### L2 — техническая

Решает:

- контейнеры;
- proxy/HTTPS;
- конфигурацию;
- backup/restore;
- server logs;
- migrations;
- disk space;
- воспроизводимость.

Использует [ADMIN_GUIDE.md](ADMIN_GUIDE.md).

### L3 — разработка

Решает:

- дефекты кода;
- изменения business rules;
- миграции;
- race conditions;
- форматы документов;
- интеграции.

## 8. Диагностика P1

### Не изменять данные вслепую

Запрещено начинать с:

- удаления volume;
- удаления `gochs.db`;
- ручного SQL UPDATE;
- удаления migration table.

### Проверить состояние контейнеров

```bash
docker compose ps
```

Для server mode:

```bash
docker compose --env-file .env -f compose.prod.yaml ps
```

### Проверить health

```text
GET /api/health
```

### Получить log

```bash
docker compose --env-file .env -f compose.prod.yaml logs gochs
```

### Проверить disk space

Убедиться, что filesystem/volume не заполнены.

### Выяснить последнее изменение

- release;
- secret;
- proxy;
- restore;
- migration;
- инфраструктура.

### Сохранить состояние

Если БД доступна, создать backup до восстановительных действий.

## 9. «Не работает вход»

Проверить:

1. не было ли пяти ошибочных попыток;
2. корректен ли secret;
3. перезапускался ли процесс;
4. используется ли правильный URL;
5. в server mode используется ли HTTPS;
6. корректно ли время;
7. server log.

При компрометации — сменить secret и перезапустить сервис.

## 10. «После обновления не запускается»

Проверить сообщения `SchemaUpgrade`.

Если схема неизвестна:

- не обходить проверку;
- сохранить БД;
- сверить версию приложения;
- использовать backup до обновления.

## 11. Ошибка 409

`409` часто означает корректно сработавшее бизнес-правило.

Примеры:

- повторный табельный номер;
- повторная выдача;
- изменение подтверждённой ведомости;
- переполнение;
- изменение подписанного занятия;
- преждевременная активация приказа.

L1 сначала проверяет состояние данных, а не сразу оформляет дефект.

## 12. Ошибка 400

Проверить:

- обязательные поля;
- даты;
- тип данных;
- JSON enum;
- CSRF token;
- срок сессии;
- upload size/type.

После длительно открытой страницы можно обновить интерфейс и войти заново.

## 13. Жизненный цикл дефекта

```text
Registered
→ Triaged
→ Reproduced
→ Fixed
→ Verified
→ Closed
```

Исправление завершено только после повторной проверки и регрессии связанных сценариев.

Если поведение изменилось, документация обновляется вместе с кодом.

## 14. Hotfix

Для P1/P2:

1. зарегистрировать проблему;
2. воспроизвести на тестовой копии;
3. подготовить минимальное исправление;
4. build;
5. релевантные integration tests;
6. backup production;
7. deployment;
8. smoke-test;
9. наблюдение;
10. закрытие/отчёт.

Рабочую БД не следует «лечить» ручным SQL вместо исправления причины.

## 15. Известные ограничения

- одна операторская модель;
- нет RBAC;
- SQLite и один процесс;
- сериализованные write-запросы;
- только внутренние уведомления;
- нет УКЭП;
- нет malware scanning;
- Swagger отключён в server mode;
- формы учебные;
- наличие тестов не является доказательством их фактического прогона.

## 16. Профилактика

Рекомендуется:

- регулярный backup;
- restore drill;
- review логов;
- контроль диска;
- прогон integration/UI перед релизом;
- обновление зависимостей;
- актуализация документации;
- review открытых P2/P3.

## 17. Инцидент безопасности

1. ограничить доступ;
2. сменить secret;
3. перезапустить;
4. сохранить logs;
5. сохранить БД и backup;
6. определить временной диапазон;
7. проверить историю операций;
8. не удалять доказательства;
9. уведомить ответственных.

Общий аудит приложения — вспомогательный источник, а не криптографически защищённый журнал non-repudiation.

## 18. Запрос на изменение

```text
запрос
→ бизнес-цель
→ impact assessment
→ решение владельца
→ разработка
→ тест
→ документация
→ релиз
```

Особенно внимательно оценивать:

- статусы;
- подпись;
- migrations;
- готовность НФГО;
- план закупок;
- документы;
- timezone;
- доступ.

## 19. Вывод версии из эксплуатации

Перед закрытием версии:

- backup;
- проверка backup;
- фиксация schema version;
- архив;
- причина вывода;
- отзыв секретов;
- выполнение требований по хранению данных.
