# План тестирования

## 1. Цель и объект

Объект проверки - объединенная учебная информационная система ГО и ЧС из репозитория `maksolodov/gochs-system`, функциональные задания 6-19 и их связи через общую SQLite-базу.

Цель - убедиться, что система запускается, основные операции доступны через интерфейс и API, данные сохраняются, ограничения предметной области соблюдаются, а ошибка одного модуля не приводит к нарушению работы остальных.

## 2. Виды проверки

| Вид | Что проверяется | Материал |
|---|---|---|
| Модульное (unit) | Правила расчета, проверки входных данных, преобразования времени, состояния СИЗ | Плановые кейсы UNIT-01..UNIT-05 в `TEST_CASES.md`. Самостоятельного unit-test проекта в текущем репозитории нет |
| Интеграционное | Запросы к API, запись в SQLite, связанные операции СИЗ, подготовки, приказов, авторизация, миграции | `tests/integration.py`, кейсы INT/SEC в `TEST_CASES.md` |
| Нагрузочное | 100, 500, 1000 параллельных GET-запросов; HTTP-ошибки, RPS, среднее, P95, P99 | `tests/load_test.py`, `LOAD_TEST.md` |
| Пользовательское (приемочное) | Вход, заполнение форм, переходы между разделами, печать/выгрузка документов | `tests/ui.cjs`, ручные кейсы и `ACCEPTANCE_CHECKLIST.md` |
| Регрессионное | Повторная проверка после исправлений | Повторный прогон ранее неудачных кейсов и ключевых сценариев |

## 3. Окружение

- Backend: ASP.NET Core 8, Entity Framework Core 8, SQLite.
- Клиент: современный браузер; браузерные автоматизированные проверки используют Playwright и Microsoft Edge.
- Локальный адрес при Docker-запуске: `http://127.0.0.1:5080`.
- Для интеграционных и UI-автотестов: .NET 8 SDK, Python 3, Node.js; для UI также Edge.
- Для нагрузочного скрипта требуется только Python 3 и локально запущенный сервер.
- Тестовые учетные данные не хранятся в репозитории.

Фактически использованные ОС, браузер, дата и хеш коммита заносятся в отчет после прогона.

## 4. Подход

1. Проверить запуск приложения и вход оператора.
2. Пройти сквозной сценарий: справочник сотрудников -> приход СИЗ -> карточка -> ведомость -> изменение статуса -> списание -> утилизация.
3. Проверить НФГО, эвакуацию, укрытия, журнал занятий и приказы.
4. Проверить отчеты и выгрузку документов.
5. Отдельно проверить отрицательные сценарии: неизвестные ID, повторное подтверждение, просроченный СИЗ, неверные размеры, попытка изменения подписанного занятия, действие без авторизации.
6. Запустить интеграционный и UI-тесты, зафиксировать вывод и фактические результаты.
7. При необходимости выполнить нагрузочные прогоны на собственной тестовой среде: 100/10, 500/25, 1000/50.
8. Зафиксировать дефекты, после исправления повторно проверить измененные и связанные сценарии.

Приоритет проверки: запуск и доступ -> сохранность данных -> выдача и списание СИЗ -> журнал -> приказы и изменение режима -> документы -> вспомогательные разделы.

## 5. Критерии приемки

- Приложение запускается и открывает основные разделы без необработанных ошибок.
- Ключевые операции создания и изменения записей сохраняются в SQLite и доступны после повторного открытия.
- Подтвержденная выдача, подписанное списание и утилизация отражаются в статусах имущества.
- Подписанные занятия и приказы защищены от запрещенных изменений.
- Активация приказа о специальном режиме влияет на связанные правила системы.
- Файлы отчетов создаются и открываются в соответствующем формате.
- Несанкционированное чтение служебных API блокируется.
- Негативные сценарии дают управляемые ошибки, а не падение приложения.
- Критические дефекты, мешающие основным сценариям, отсутствуют на момент приемки.

Нагрузочные показатели фиксируются по факту; жесткие пороги P95/P99 исходное задание для данного приложения не устанавливает. Отдельный нагрузочный прогон на 100 запросов уже предусмотрен в интеграционном скрипте, но его наличие не подтверждает фактическое выполнение.

## 6. Учет результатов

Каждый тест-кейс из `TEST_CASES.md` получает статус: `PASS` / `FAIL` / `BLOCKED` / `NOT RUN`.

- PASS - ожидаемый результат действительно получен.
- FAIL - наблюдается отличие, оформляется дефект.
- BLOCKED - проверка невозможна из-за внешней проблемы или отсутствующих данных.
- NOT RUN - проверка еще не проводилась.

Данные автоматических прогонов, версии приложения, найденные дефекты и общие выводы записываются в `TEST_REPORT.md` или в его заполненную копию. **Не заменяйте `NOT RUN` на `PASS` без выполнения проверки.**
