# Будущее серверное размещение

Конфигурация для размещения за HTTPS-прокси. Контейнеры и выпуск сертификата на удаленном сервере не проверены.

## Настройки

Нужны сервер с Docker Compose, доступ администратора развертывания, выделенное DNS-имя и разрешенный входящий HTTPS. Конфигурация рассчитана на Caddy как единственный внешний прокси. HTTP обслуживается только прокси для перенаправления на HTTPS и проверки сертификата; порт приложения наружу не публикуется.

Скопируйте `.env.example` в `.env` и заполните:

| Переменная | Значение |
|---|---|
| DOMAIN | Реальное DNS-имя без схемы, порта и пути; используется также как AllowedHosts |
| ACME_EMAIL | Адрес ответственного за сертификат |
| BIND_ADDRESS | Разрешенный адрес интерфейса сервера для прокси |
| HTTP_PORT / HTTPS_PORT | По умолчанию 80 / 443; при других портах требуется внешнее перенаправление стандартных портов для проверки сертификата |
| PROXY_SUBNET | Свободная частная IPv4-подсеть Docker, не пересекающаяся с сетями сервера |
| PROXY_IP | Свободный адрес внутри этой подсети, закрепленный только за Caddy |
| OPERATOR_PASSWORD_FILE | Абсолютный путь к файлу секрета вне репозитория |
| SESSION_MINUTES | Срок сессии от 1 до 480 минут, по умолчанию 120 |

Создайте случайный пароль не короче 16 символов в файле секрета. Не помещайте пароль в `.env`, Git или командную строку. Файл должен читаться пользователем `app` контейнера (.NET 8, UID 1654), но не остальными пользователями сервера. Для Linux задайте владельца 1654 и права 0400; Compose монтирует его только на чтение. Секрет не включается в образ. `.env` содержит пути и конфигурацию, тоже храните его с ограниченными правами.

## Запуск

Используйте серверный файл отдельно, не объединяйте его с локальным `compose.yaml`:

```sh
docker compose --env-file .env -f compose.prod.yaml config --quiet
docker compose --env-file .env -f compose.prod.yaml up --build -d
```

Caddy получает сертификат для DOMAIN и передает запросы приложению внутри закрытой сети. ASP.NET доверяет forwarded-заголовкам только от PROXY_IP. Cookies в серверном режиме имеют Secure, HttpOnly, SameSite Strict. Swagger выключен. Пароль не задан, доверенный прокси не настроен или AllowedHosts содержит `*` - приложение откажется запускаться.

Проверки после размещения: `/api/health` возвращает только `{"status":"ok"}`; `/api/employees` без входа возвращает 401; HTTP перенаправляется на HTTPS; после входа работают формы и загрузка PDF/PNG/JPEG; без CSRF-токена запись отклоняется; после выхода прямые ссылки на документы закрыты. Проверьте сертификат и Secure у cookie средствами браузера. Данные должны сохраняться после `docker compose ... restart gochs`. Не запускайте несколько экземпляров приложения на одной SQLite.

## Копия и восстановление

База и ключи находятся в постоянном томе `gochs-data`. Ручные копии - в `gochs-backups`. Для работающего приложения:

```sh
docker compose --env-file .env -f compose.prod.yaml exec gochs dotnet Gochs.dll --backup /app/backups/manual.db
docker compose --env-file .env -f compose.prod.yaml cp gochs:/app/backups/manual.db ./manual.db
```

Используйте новое имя каждой копии. Копирование выполняется SQLite Backup API и учитывает WAL. Настройте запуск этой команды штатным планировщиком сервера, например ежедневно, и копирование результата на отдельный защищенный носитель. Автоматического внешнего хранилища в проекте нет. Периодически проверяйте восстановление в отдельном стенде. Хранение резервной копии только на том же диске не защищает от потери сервера.

Для восстановления файл должен быть доступен в томе `gochs-backups`. Остановите приложение, выполните восстановление отдельным контейнером без опубликованных портов и снова запустите:

```sh
docker compose --env-file .env -f compose.prod.yaml stop gochs
docker compose --env-file .env -f compose.prod.yaml run --rm --no-deps gochs --restore /app/backups/manual.db
docker compose --env-file .env -f compose.prod.yaml up -d gochs
```

Команда запускает entrypoint `dotnet Gochs.dll`. Перед восстановлением проверяется целостность копии и сохраняется прежняя база. Если файл лежит на хосте, предварительно скопируйте его в том через работающий контейнер командой `docker compose ... cp ./manual.db gochs:/app/backups/manual.db`, затем остановите приложение. Не применяйте `down -v` и не копируйте занятую SQLite обычной файловой командой.

Перед обновлением образа сохраните копию, затем остановите приложение и выполните `up --build -d`. SQL-миграции выполняются при старте; перед изменением прежней схемы есть дополнительная копия в `/app/data/backups`. При неизвестной схеме приложение останавливается. Для отката к старому коду используйте соответствующую ему резервную копию, не запускайте старый код на новой схеме вслепую.

Один оператор видит все записи. Для ограниченного доступа преподавателя используйте отдельный секрет и при необходимости правила доступа на стороне сервера. Это не система с разграничением по подразделениям и не аттестованное хранилище закрытых сведений.

## Резервная копия без Docker

Из каталога `backend`, после сборки Release:

```sh
dotnet build -c Release
dotnet bin/Release/net8.0/Gochs.dll --backup ../data/backups/manual.db
```

Копию можно создавать при работающем приложении. Для восстановления сначала остановите его:

```sh
dotnet bin/Release/net8.0/Gochs.dll --restore ../data/backups/manual.db
```

Используйте свободное имя для каждой новой копии. Команда восстановления сохраняет предыдущую базу перед заменой.
